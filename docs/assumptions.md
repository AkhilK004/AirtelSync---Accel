# Assumptions & deviations from PLAN.md

| # | Item | Decision |
|---|---|---|
| A1 | Data location | Dataset copied to `data/raw/` (original `YTL_TrackA_Udyam_Digital_Data/` left untouched). |
| A2 | City tiers | Data has tiers 1 and 2 only (plan assumed 3). Tier-3 handling in advisor = treat unknown city as the least-served tier (2) with an assumption note. |
| A3 | Price range meaning | **Resolved:** unit price = midpoint of [min,max], rounded half-up to a whole rupee (`PRICE_POINT_RULE=midpoint`). Calibrated on 368 activated leads: bundle value / sum(midpoint x qty) has median 0.992 (min-rule 1.14, max-rule 0.88); 74% within +/-5%. Show this rule on the pricing slide. |
| A4 | Dependencies | `requires_one_of` is OR semantics (at least one SKU). Plan's "closure" is adapted accordingly. |
| A5 | Size limits | Catalogue has only `min_employees`/`min_sites` (no max). Plan's `SIZE_TOO_LARGE` code is unused. |
| A6 | Languages | Data has 10 languages; UI ships en, hi, mr per plan. Others fall back to English/Hindi. |
| A7 | Whether prices include GST | **Resolved: exclusive.** `monthly_bundle_value_inr` of activated leads equals the pre-GST midpoint total (A3), so GST (18%, config) is added on top, rounded half-up in paise. |
| A8 | Tooling | `uv` not installed system-wide; installed via `pip install uv`, invoked as `python -m uv`. Python 3.12 managed by uv. |
| A9 | shadcn toast | shadcn deprecated `toast`; `sonner` used instead. |
| A10 | GSTIN checksum | 100% of registry passes -> enforced as FAIL (PLAN rule 4). |
| A11 | "Today" | 2026-07-15 (`settings.TODAY`) for bill recency / expiry checks. |
| A12 | Git | `web/` was created with its own `.git` by create-next-app; handled in phase commit (see README of phase report). |
| A13 | Quantity semantics | Calibrated on activated bundles: `bundle_products` qty is the billed quantity; per-site products have qty = number of sites (95% for per-site); setup fee = setup x qty (100% match, so **no extra sites multiplier**); bundle contract = max of line contracts (100% match). |
| A14 | Segments | Business type -> segment is read from leads (every business_type maps to exactly one segment). Multi-site = 3-12 sites in data, so `MULTI_SITE_MIN_LOCATIONS=3`. Manufacturers (12-150 staff) and `locations > 10` are `assisted`. A chain business type with <3 locations is treated as professional (>6 staff) or micro. Unknown business type: sized by team (<=6 micro else professional) + assumption note. |
| A15 | Bundle templates | `api/config/bundles.yaml` maps needs -> catalogue SKUs per segment. Choice of core vs optional follows what activated leads buy (e.g. 100% of professionals buy cloud email P16 and most buy endpoint security P20 -> required; failover/CCTV/backup optional). Quantities: staff-ratio rules (e.g. SIMs ~0.33 x staff for offices, email/security = staff). These are judgement calls informed by data, not catalogue facts. |
| A16 | Tier choice | Smallest eligible tier whose `fits_up_to` covers team size; if the preferred tier is ineligible (e.g. 1G in tier-2), next-best eligible tier is used and the exclusion is reported. Fixed wireless (P04) is a fallback used only when no fibre/leased line is eligible or fibre is unavailable. |
| A17 | Dependencies in quotes | Core lines and pre-selected add-ons get dependency closure at recommendation time (cheapest eligible provider, else dependent dropped with `DEPENDENCY_INELIGIBLE`). Other add-ons resolve at toggle time: ON pulls in the cheapest eligible provider; OFF removes dependents. Fibre SKUs are blocked as providers when `fibre_available=false`. |
| A18 | GSTIN eligibility | `requires_gstin` products need `gstin_status == active`. "Applied", "inactive" (Cancelled/Suspended) and none all block them with distinct messages. |
| A19 | Mock latency | 300-600 ms random delay on `/mock/*` (config `MOCK_LATENCY_MS_*`, 0 in tests). |
| A20 | Generic business types | Business types outside the leads data fall back to keyword rules (`MANUFACTURING_KEYWORDS`, `PROFESSIONAL_KEYWORDS` in `config.py`), then to team size (<=6 micro, else professional) with a visible assumption. |
| A21 | Advisor questions | 5 required slots (type, team, locations, city, GSTIN) asked in fixed order; the 6th question (current tools) is asked **after** the recommendation as a refinement so a one-shot message can be answered in 1-2 replies. Max 6 questions is enforced; when spent, remaining slots get defaults + visible assumptions (employees 2, locations 1, tier-2, no GSTIN). |
| A22 | Unknown city / tier 3 | Cities come from `data/derived/city_tiers.json` (the 22 cities in the leads, tier 1 or 2). Unknown city -> tier-2 with the `city_unknown` assumption instead of a pincode question (no pincode->tier source exists in the data). |
| A23 | Chips -> numbers | Range chips send text the NLU parses: midpoint rounded up (1-2=2, 3-5=4, 6-10=8, 11-25=18); "N+" = N*1.6 for employees (25+=40), N+1 for locations (10+=11). |
| A24 | Offline NLU/NLG | `LLM_PROVIDER=fake` uses `app/llm/rules_nlu.py` (regex NLU for en/Hinglish/hi/mr) and template NLG. The same rule NLU is the runtime fallback if a live LLM call fails or times out. The 17 scenarios pass offline; **they have not yet been run against Gemini** (no GCP credentials in this environment). |
| A25 | Leased line requests | Customer asks for a leased line: if P05/P06 are ineligible the reply states why (GSTIN, 10+/25+ people) and offers fibre / 5G; if eligible but not a manufacturer, the reply says a site survey is needed. The bundle itself is unchanged. |
| A26 | Product names in hi/mr | `data/derived/catalogue_i18n.json` holds hand-authored transliterated names; they have not been reviewed by a native speaker. |
| A27 | Next.js config | This scaffold ships Next 16 with `cacheComponents`/`partialPrefetching` on; both turned off because every data screen is client-fetched from the API. `middleware` is now `proxy.ts` (redirects locale-less paths using Accept-Language, skips `/backoffice`). next-intl needs `i18n/request.ts` + plugin even with a client provider. |
| A28 | Checkout date window | Slot dates are validated against `settings.TODAY` (2026-07-15, dataset "today"), not the wall clock; the UI reads it from `GET /meta`. Mock OTP is `123456` (config `MOCK_OTP`), accepted for any valid Indian mobile. Checkout creates the order record with state `PLACED` and a frozen quote snapshot; the Phase 6 state machine builds on it. Only the phone's last 4 digits and a salted hash are stored. |
| A29 | Quote localisation | `GET/POST /quotes...?lang=en|hi|mr` returns localised names, one-line reasons, assumption and toggle-notice text. Prices are identical in every language (tested). |
| A30 | Signatory vs registry | The GST registry holds a person's name only for proprietorships ("Name (Prop. Business)"). For those, the ID name must match (fuzzy >= 85, else FAIL -> manual review). For LLPs / Pvt Ltd the registry has no individual names, so `SIGNATORY_MATCH` passes with the note "ID is issued for your business" (the ID's "For business" is still name-matched). This is a judgement call; a real build would use DIN/partner lists or e-sign. |
| A31 | UDYAM_CATEGORY not enforced | Calibrated on 2,723 leads with a Udyam record: enterprise type (Micro/Small/Medium) is uncorrelated with headcount (e.g. 25+ staff: 59% Micro, 35% Small). Enforcing PLAN's WARN would raise false alarms, so the check is not emitted. |
| A32 | Udyam date not compared | The registration date printed on all 11 Udyam certificates differs from the registry record, so it is not a usable tampering signal in this dataset. Name, number format and registry existence are checked instead. |
| A33 | Calibrated thresholds | GSTIN checksum 100% on registry -> FAIL. GSTIN state code vs registry state 100% -> WARN on mismatch. Trade name vs Udyam name: exact match for all 2,723 linked leads -> `NAME_MATCH` thresholds 90/75 are safe. Blur: Laplacian variance of 46 sharp specimens >= 930, the blurred one = 1.0 -> `BLUR_THRESHOLD=100`, min side 600 px. |
| A34 | KYC extraction in tests | No Gemini credentials were available. `data/derived/kyc_fixture.json` is MY transcription of the 47 specimen images (built by `scripts/build_kyc_fixture.py`), served by FakeLLM by file hash. It proves the validators and decisions, **not live OCR accuracy**. The blurred K04 certificate is encoded as unreadable (confidence 0.3). Unknown images are "unreadable" offline. Live check: `python -m uv run python ../scripts/eval_kyc.py --provider gemini`. |
| A35 | `kyc_expected.csv` is a DRAFT | Written by me from looking at the images, BEFORE the first run (it matched 12/12 without tuning). A human must verify it. Judgement calls to check: K02 (skewed but readable scan -> APPROVED), K05 (no Udyam certificate on the GSTIN path -> APPROVED), K10 (LLP signatory cannot be matched -> APPROVED), K07 issue codes. |
| A36 | Specimen findings | K01 GSTIN is Cancelled in the registry and the Udyam certificate prints no number -> REJECTED. K02 certificate scanned at an angle (readable). K04 GST certificate blurred -> re-upload. K05 has no Udyam certificate. K06 printed GSTIN `08YKZXS8189L1ZO` has a wrong digit (registry `08YKZXS5189L1ZO`) -> checksum fail, re-enter. K07 certificate legal name "Shri Physio Clinic" vs registry "Neelgiri Physio Clinic" -> tampering signal -> manual review. K11 bill dated 2025-10-31 (> 90 days before 2026-07-15) -> newer bill. K03, K08, K09, K10, K12 clean. Note 0/O look identical in the monospace font: GSTINs of K02, K04, K06 and K08 contain the letter O. |
| A37 | Signatory ID type | The specimens carry a synthetic "SYN-ID-######" signatory card (name, designation, business, valid till), not PAN/Aadhaar. `ID_FORMAT` accepts that pattern; PAN (entity code A,B,C,F,G,H,L,J,P,T or X), Aadhaar (Verhoeff, masked to last 4 immediately) and DL/passport/voter (format not checkable, WARN) are also handled. The PAN + bill path is shown as "coming soon" (PLAN cut-line); the Udyam-only path exists in the API/UI. |
| A38 | Review images | Uploaded images are processed in process memory only. They are kept in memory until the owner presses "Check my documents"; only on `MANUAL_REVIEW` are they written to the review store (local `api/.review_store`, or the GCS bucket in prod with a 1-day lifecycle) and `purge_expired()` deletes local files after 24 h. Pending images are per instance: Cloud Run needs `--max-instances 1` or session affinity (note for Phase 8). |
| A39 | Consent ledger | Append-only records `{id, kind grant|withdraw, order_id, principal_ref (salted sha256 of phone), purposes, notice_version "2026-07-v1", language, timestamp, channel}`. Effective consent = replay of the ledger. Marketing and partner sharing are off by default and unbundled; required purposes must both be ticked. Withdrawing `kyc_verification` blocks all KYC endpoints (403). `partner_sharing` is only offered with `?partner=true`. |
| A40 | Order states from KYC | Until Phase 6 builds the state machine, KYC sets the order state directly: APPROVED -> `KYC_VERIFIED`, ACTION_REQUIRED -> `KYC_ACTION_REQUIRED`, MANUAL_REVIEW -> `KYC_REVIEW` (+ lead, + audit entry), REJECTED -> `CANCELLED` (`cancel_reason=kyc_rejected`). |
| A41 | Fulfilment modes | `api/config/fulfilment.yaml` lists the instant-digital SKUs (P14 SMS, P15 WhatsApp API, P16 email, P17 backup, P18 website, P20 endpoint security). Everything else is physical and follows install steps, with lead time = catalogue `typical_install_days` (SIM lines, static IP, telephony, POS, CCTV, firewall, Wi-Fi are therefore "physical"). This is a judgement call on the plan's category examples. |
| A42 | Auto-scheduling | The customer already chose an install slot at checkout, so when KYC passes the order goes `KYC_VERIFIED` -> `INSTALL_SCHEDULED` automatically (two events). Technician assignment, installation and activation are ops-driven (demo "advance"). An order with only digital lines goes `KYC_VERIFIED` -> `ACTIVATED` at once. |
| A43 | Transitions | Table in `app/orders/state.py` (tested exhaustively). KYC states can move among each other (a re-upload may land anywhere in the KYC family); `ON_HOLD` can only resume to the state it was held from; `TECHNICIAN_ASSIGNED` -> `INSTALL_SCHEDULED` is a reschedule; `ACTIVATED` and `CANCELLED` are final. KYC re-evaluations after the order left the KYC family are ignored. |
| A44 | ETAs | Dates come from SLA constants plus the chosen slot: KYC +1 day; install scheduled KYC +1; technician = install day -1; installed = max(slot, KYC + longest line lead time); active = installed. Done steps show their real date. Computed on the demo clock (`settings.TODAY`, see `app/clock.py`), so event dates read 2026-07-15 onward. |
| A45 | Tracker access | Light check only (plan): last 4 digits of the checkout phone. Stored in `sessionStorage` after checkout so the tracker opens directly; otherwise it asks. `track=true` on the first page load logs `tracker_viewed`; the 5 s polls do not, so the "status checks per order" metric is not inflated. Demo advance (`?demo=1`) needs `NEXT_PUBLIC_DEMO_ADMIN_TOKEN` in the build. Notifications are simulated (WhatsApp by default, SMS for hold / cancel / action required) and stored as events, rendered in the viewer's language. |
| A46 | API shape | `POST /checkout` is the plan's `POST /orders`. Added `POST /orders/{id}/reschedule` and `/callback` (customer, last-4 check) and `/admin/orders/{id}/{advance,reschedule,hold,cancel}` (X-Admin-Token, audit-logged). Technician names are mock constants. |
| A47 | Lead scoring inputs | The propensity model needs creation-time features. For live leads they are built from the advisor session (or the quote profile) in `app/leads/scoring.py`. Never asked, so imputed: annual turnover = most common band ("40 lakh - 1.5 cr"), monthly telecom spend = segment median from the data, products of interest = number of wanted extras (min 1), has_udyam = false, source = Website form / WhatsApp / Channel partner (from channel and partner code). Imputation makes live scores less sharp than the 0.70-AUC test; seeded leads use their real CSV row. Score is a ranking aid, not a forecast. |
| A48 | Lead sources | Leads are created by: handoff / assisted segment (advisor), KYC MANUAL_REVIEW or REJECTED (at decision), order callback requests, and lazily at list time for sessions idle > `ABANDON_MINUTES` (abandoned, or `quote_not_accepted` if a quote was shown and no order exists for it) and orders stuck in `KYC_ACTION_REQUIRED` > 24 h. `refresh()` is idempotent. "Price" is only a seeded reason (mapped from CSV drop reasons); the live system cannot know why a quote was not accepted. |
| A49 | Routing (MOCK directory) | `api/config/routing.yaml`: field force owns multi-site, manufacturer and assisted leads (partner attribution kept); partners get leads carrying their code or located in their cities; telesales gets the rest. Partner codes/names and the state -> field-team regions are fictional. The "territory team" column credits digital sales in a territory to that team. |
| A50 | Funnel panel | Counts distinct ids from the event log: advisor_started, recommendation_shown, quote_accepted, order_placed (checkout), kyc_complete (KYC APPROVED), activated. Baselines (7.4%, 44%, 17.6 days, 3 checks) and targets (14%, 65%, 5 days, 0.5) come from `docs/findings.md` and the business case. Seeded events are flagged `props.seed` and the panel states how many events are seed data (the demo seed shows 3.3% lead-to-activation only because 1 of 30 seeded leads activates; it is not a result). |
| A51 | Demo seed | `SEED_ON_START=true` (or `POST /admin/reset` with the admin token) creates 30 leads from real `smb_leads.csv` rows (deterministic sample, scored by the real model, re-dated to the last ~6 days) and 3 live orders (KYC action required, technician assigned, active; phones ending 0001-0003) with dates spread so median time-to-activate is non-zero. The stuck-KYC demo order also surfaces as a 31st lead after the 24 h rule. In-memory store: data is lost on restart (Firestore arrives in Phase 8). |
| A52 | Back-office access | HTTP Basic (`BACKOFFICE_USER` / `BACKOFFICE_PASSWORD`), constant-time compare, English-only UI with its own login form (credentials kept in `sessionStorage` for the tab). Lead status changes are audit-logged with the actor. Phone numbers are masked except the last 4 digits. |
| A53 | One clock | `advisor.models.now_iso()` now delegates to `app/clock.py`, so sessions, events, consents, orders and leads share the demo clock (dataset "today" + real time of day). |
| A54 | Deploy skipped | `scripts/deploy_gcp.sh` is written and dry-run-printed but **not executed**: no hackathon GCP project was provided (gcloud only had an unrelated project). Needs your project id + billing; see `docs/deploy.md`. Vercel is an alternative for the web app. |
| A55 | Firestore untested live | `FirestoreRepo` is verified only against an in-memory fake client (put/get/list/append-only/clear). Composite indexes are not needed (no queries beyond full-collection streams, which will get slower as events grow; fine for a demo). |
| A56 | Rate limits | Per client IP, in memory, per instance (Cloud Run is pinned to 1 instance): session create 30/min, chat messages 120/min (+80 per session), KYC 60/min, OTP 10/min, checkout 20/min, consents 30/min. Shared office NATs share a bucket. Disabled in tests via `RATE_LIMIT_ENABLED=false`. |
